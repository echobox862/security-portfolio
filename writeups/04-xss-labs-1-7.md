## 一、七关全景：一条"过滤越来越狠"的绕过线

| 关卡 | 过滤情况 | 输出的位置（上下文） | 绕过要点 |
|---|---|---|---|
| Less 1 | **无过滤** | HTML 文本 | 直接注入脚本即可执行 |
| Less 2 | 无过滤，但内容落在**属性值里** | `input` 标签的 `value` 中 | **先闭合标签/属性**，再注入 |
| Less 3 | 对 `alert` 等危险字符做**清除** | HTML 文本 | 把 `alert` **双写** |
| Less 4 | 遇到 `alert` 直接**终止脚本执行** | HTML 文本 | 换用其他弹窗函数（如 `prompt()`） |
| Less 5 | 清除 `script`、`alert`、`on`、`img` 等 | HTML 文本 | 危险字符**双写** |
| Less 6 | 清除范围更大：`script`、`alert`、`on`、`img`、`<`、`src` …… | HTML 文本 | ① 改用**事件**（`onclick`）② 按**字符删除顺序**设计双写 |
| Less 7 | **无过滤** | **存入数据库**，其他页面查询时输出 | **存储型 XSS**，无用户交互即触发 |

**这条线的教学价值**：它把 XSS 的两个核心变量隔离出来单独练——

- **输出的上下文**（Less 1 的文本 vs Less 2 的属性值）
- **过滤的强度**（Less 1 → Less 6 逐级加强）

**理解这两者的组合方式，比记住七种 payload 有用得多。**

## 二、第一梯队：上下文决定 payload 形态（Less 1–2）

### 2.1 Less 1：HTML 文本上下文，无过滤

输入的内容被直接输出到页面 HTML 中，浏览器按 HTML 语法解析——**尖括号被当成标签、脚本被执行**。这一关之所以成立，根因是**服务端完全没有对输出做处理**。

### 2.2 Less 2：属性值上下文，需要先"逃出去"

**这一关的现象非常典型，值得记住**：输入的内容被放进了 `input` 标签的 `value` 属性里——输入 `yunyansec`，查看源码就能看到它出现在 `value="..."` 中间。

**为什么"直接写脚本"在这里无效**：因为此刻 payload 处在**属性值上下文**中。浏览器已经把它当"属性值"开始解析了，里面的 `<script>` 只是普通字符串，不会被当成标签。

**正确思路是先闭合属性、再注入**：

```
先闭合属性并结束标签：  ">  或  " onclick=...
再注入脚本
```

> **这是全篇最重要的一处认知**：**同一个 payload 在不同上下文里，有效性完全不同。**
> 所以防御侧的标准做法也不是"过滤危险字符"，而是**按输出位置选择对应的编码方式**（HTML 文本编码、属性编码、JS 编码、URL 编码各不相同）——**因为"危险"是由上下文定义的，不是由字符定义的**。

## 三、第二梯队：过滤器缺陷的绕过（Less 3–6）

这四关的过滤强度递增，但**绕过原理高度一致**——都在利用同一类实现缺陷。

### 3.1 Less 3 / Less 5：双写绕过

**现象**：包含 `alert`（Less 3）、或 `script`/`alert`/`on`/`img`（Less 5）的内容会被清除。

**绕过**：把这些关键词**双写**。

**原理**：过滤逻辑是"把命中的关键词替换为空"，而且**只执行一次**。那么构造一个"经过一次替换后恰好剩下完整关键词"的输入即可：

```
alalertert   →  一次替换删掉中间的 alert  →  剩下 alert
```

> **这与 SQL 注入里的关键字双写（`UNIunionON` → `UNION`）、文件上传里的后缀双写（`pphphp` → `php`）是同一个原理的三种形态。**
> **根因都是"过滤是一次性字符串替换"**。对应的正确修复是**循环替换到不再变化**，或者——更好的做法——**改用输出编码而不是过滤**。

### 3.2 Less 4：换函数绕过

**现象**：包含 `alert` 会直接**终止脚本执行**（不是删除，是让整段脚本不跑）。

**绕过**：改用其他弹窗函数，例如 `prompt()`——它同样会弹出对话框，但不在过滤名单里。

**原理**：这是**黑名单的固有缺陷**——黑名单只能列举"已知的危险项"，而"能实现同一效果的手段"是枚举不完的。名单里有 `alert`，就有 `prompt`、`confirm`、`console.log`……

> **这正是黑名单与白名单的根本差异**：白名单"只允许已知安全的"，逻辑上不会漏；黑名单"只拒绝已知危险的"，**永远列不全**。Less 4 用一个函数替换就证明了这一点。

### 3.3 Less 6：换事件 + 利用过滤顺序

**现象**：过滤名单扩大到 `script`、`alert`、`on`、`img`、`<`、`src` 等更多字符。

**两条绕过思路**：

1. **改用事件触发**：`onclick` 这类事件在元素被点击时才执行，**不依赖 `<script>` 标签**，也不依赖 `img` 这类被拦的标签
2. **按"字符删除顺序"设计双写**：既然过滤是**按顺序依次删除**多个关键词，那么构造时就要考虑**删除的先后关系**——先被删掉的词，可能在删除后**恰好拼出**下一个要被删的词。**必须按实际删除顺序来排列 payload，顺序错了就拼不出目标**

> **第 2 点比第 1 点更值得记**：它说明**绕过不是"随便加点东西"，而是要先逆向出过滤器的处理顺序，再据此构造输入**。
> 这和 `Python tamper编写` 里那条结论完全一致：**tamper 的验收标准是"数据库仍能正确执行"——绕过要精确，不能靠碰运气**。

## 四、第三梯队：存储型 XSS（Less 7）★

**现象**：这一关**没有增加任何过滤**，但输入的内容会被**直接保存到数据库中**；当其他页面查询并展示这条数据时，脚本在访问者的浏览器中执行。

**复现要点**：

1. 在留言/提交处输入 payload（含脚本）
2. 提交后数据入库
3. **换到查询页面，检索刚才提交的 id**
4. 查询结果渲染时脚本执行——弹窗触发

**为什么存储型的危害量级高于反射型**：

| 对比项 | 反射型 | 存储型 |
|---|---|---|
| payload 存放位置 | URL / 请求参数 | **数据库** |
| 触发方式 | 需要诱导受害者点击构造好的链接 | **任何访问该页面的用户都会中招** |
| 影响范围 | 单次、单人 | **长期存在、影响所有访问者（含管理员）** |
| 典型攻击目标 | 钓鱼、诱导点击 | **打管理后台会话、批量影响用户** |

> **关键点**：存储型 XSS 的 payload **持久化**了——数据入库一次，之后**每一次被展示都会重新触发**。这也是为什么在需要"后台人工审核"的功能（留言、昵称、订单备注、工单）里放存储型 XSS，实战中通常用于**获取管理员会话**。

## 五、实验结果总结

本次实验验证了 XSS 的两种基本形态与实际利用效果：

- **反射型**：payload 随请求即时回显并执行（Less 1–6）
- **存储型**：payload 入库，在后续查询时执行（Less 7）
- 实验中利用恶意脚本实现了**弹窗触发**与**Cookie 窃取**的模拟攻击

**七关练下来，真正沉淀的是一条判断顺序**：

```
① payload 落在什么上下文？（HTML 文本 / 属性值 / JS / URL）
  → 决定需不需要"先闭合"
② 有什么过滤？（无 / 清除关键词 / 终止执行）
  → 决定用"双写 / 换函数 / 换事件"
③ 是反射还是存储？
  → 决定危害量级与影响范围
```

## 六、危害

- **会话劫持**：脚本可读取页面中的敏感信息，若 Cookie 未加 `HttpOnly`，可直接窃取会话凭证
- **钓鱼与页面篡改**：在可信页面中插入伪造表单、诱导操作
- **打管理后台**：存储型 XSS 配合管理员访问，可提升为后台权限操作
- **蠕虫式传播**：在社交类功能中，存储型 XSS 可自我复制、批量扩散

## 七、修复建议

| 优先级 | 措施 | 说明 |
|---|---|---|
| **①（根治）** | **按输出上下文做编码** | HTML 文本、属性、JS、URL 各用对应编码。**"危险"由上下文定义，所以编码也必须按上下文做** |
| **②** | **CSP（内容安全策略）** | 白名单化脚本来源，让"即使注入成功也执行不了" |
| **③** | **Cookie 加 `HttpOnly`** | 直接砍掉 XSS 最主要的收益（窃取会话） |
| ④ | 前端新项目启用 **Trusted Types** | 浏览器层面禁止把字符串直接写入危险位置 |
| ⑤ | 输入校验（白名单） | **只能作为辅助**，"过滤特殊字符"这条路已被 Less 3–6 证明会被绕过 |

**结论（本实验的直接推论）**：Less 3–6 这四关其实是**对"黑名单过滤方案"的连续反证**——每加一层过滤，就多一种绕过。**所以修复的重心必须从"过滤输入"移到"编码输出 + 限制执行"。**

## 八、延伸

**三条可以迁移的判断**：

1. **先看上下文，再谈 payload**。Less 2 说明了：同一个 payload 在文本里有效、在属性里无效。真实测试中，"输出到哪里"比"用了什么 payload"更重要。
2. **黑名单一定被绕过，只是时间问题**。Less 4 用一次函数替换就证明了——**评估防御方案时，"这是黑名单"本身就是一条风险项**。
3. **反射型与存储型要分开定级**。同样是弹窗，存储型因为"持久 + 影响所有访问者"，风险量级完全不同——**定级时看的是影响范围，不是 payload 复杂度**。
