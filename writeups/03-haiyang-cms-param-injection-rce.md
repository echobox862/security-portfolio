## 一、先做一处归类修正（值得记的一个细节）

原实验报告的"实验结果总结"把这条归为**文件上传漏洞**，但从 payload 结构看，**它实际是"参数被当成模板表达式解析"导致的任意代码执行**，与文件上传无关。

**为什么要较这个真**：漏洞归类会直接决定修复方向——

- 若认为是**上传漏洞**，修复动作会落在"加后缀白名单、上传目录禁执行"——**这套措施对这个漏洞完全无效**，因为根本没有文件上传点
- 若认定为**参数注入 / 模板解析注入**，修复动作才是"不把用户输入当变量名解析、危险函数禁用、升级到已修复版本"——**这才是对症的**

> **这是本次实验中最值得带走的一条意识**：**报漏洞时，"它属于哪一类"直接决定"它该怎么修"。归类错了，修复建议就会全错。**

## 二、现象

目标站点为海洋影视系统。在搜索功能处构造特定参数后，服务端返回内容发生变化，说明参数被服务端代码解析并执行；进一步构造后可在服务器上写入 WebShell，并通过工具连接取得控制权限。

## 三、原理

### 3.1 成因

海洋 CMS 的搜索功能在处理 `searchpage` 相关参数时，会把**用户传入的值当作"模板变量名"参与字符串拼接与替换**，而没有做白名单校验。这使得攻击者可以：

1. 用一个参数控制**另一个参数的名字**
2. 借助嵌套结构触发解析器的二次处理
3. 最终**把散落在多个参数里的片段拼成一段可执行代码**

**本质与我们学过的 SSTI（服务端模板注入）同源**：**用户输入进入了"模板/变量解析"环节，而不是仅仅作为数据被处理**。区别只是这里有具体的 CMS 实现作为载体。

### 3.2 payload 拆解：它到底是怎么拼出危险代码的

原实验使用的 payload（保持原样）：

```
searchtype=5
&searchword={if{searchpage:year}&year=:e{searchpage:area}}&area=v{searchpage:letter}&letter=al{searchpage:lang}
&yuyan=(join{searchpage:jq}&jq=($_P{searchpage:ver}&&ver=OST[9]))&9[]=sy&9[]=
```

**关键在于 `{searchpage:xxx}` 这种写法会被解析成 GET 参数 `xxx` 的值**，于是各参数互相引用、逐层展开：

| 参数 | 值 | 展开后得到的片段 |
|---|---|---|
| `year` | `:e{searchpage:area}` | `:e` + `v` |
| `area` | `v{searchpage:letter}` | `v` + `al` |
| `letter` | `al{searchpage:lang}` | `al` + （空） |
| → 拼合结果 | | **`:eval`** |
| `jq` | `($_P{searchpage:ver}` | `($_P` + `OST[9]` |
| `ver` | `OST[9]` | `OST[9]` |
| → 拼合结果 | | **`($_POST[9])`** |

最终由 `{if ...}` 结构触发解析，等效执行：

```
eval($_POST[9])            ← 一个由 POST 参数控制入口的代码执行点
```

（payload 末尾的 `9[]=sy` 是为 POST 参数占位，便于后续替换内容。）

### 3.3 这个 payload 的设计思想（我认为最值钱的一点）

**它把 `eval` 和 `$_POST` 这两个必然会被 WAF 拦截的关键词，拆成多个无害碎片分散到不同参数里，靠程序自身的变量替换机制再拼回完整形式。**

- WAF 在每个参数上看到的是 `:e`、`v`、`al`、`($_P`、`OST[9]`——**没有一个是危险词**
- 而程序在解析阶段把它们拼成 `:eval` 与 `($_POST[9])`——**完整危险代码**

**这与我们学过的两类绕过完全同源**：

| 手法 | 过滤器看到的 | 程序实际执行的 |
|---|---|---|
| sqlmap tamper 关键字双写 | `UNIunionON` | `UNION` |
| 命令执行变量拼接 | `$a$b`（`a=l;b=s`） | `ls` |
| **本 payload 参数交叉引用** | 无害碎片 | `eval($_POST[9])` |

> **统一的原理再次出现**：**过滤发生在字符串层，而执行发生在解析/语义层——两者不一致处就是缝隙。** 这条 payload 是这个原理最"工程化"的一种表达。

## 四、复现步骤

1. 访问靶场环境，确认目标为海洋影视系统
2. 定位搜索功能，用 Burp Suite 抓取搜索请求
3. 构造并提交上述 payload，观察响应——**有返回内容说明解析成功**
4. 利用该执行点写入木马文件
5. 用 HackBar 验证木马文件是否写入成功、能否访问
6. 使用 WebShell 管理工具连接，获得命令执行能力
7. 在 Web 根目录下定位并读取目标文件（flag）

**关键点（脱敏）**

```
请求：搜索接口，提交上述 searchtype / searchword 组合参数
验证：HackBar 直接访问写入的文件，确认可解析
连接：WebShell 管理工具连接该文件
取证：在 Web 根目录（WWW）下读取到 flag
```

## 五、危害

- **远程代码执行（RCE）**：无需登录、无需任何前置权限，直接取得代码执行能力
- **服务器完全失陷**：可读写任意文件、执行系统命令
- **业务数据泄露**：CMS 配置文件中的数据库凭据、站点数据
- **横向渗透**：以此服务器为跳板探测内网
- 本例中从"一个搜索参数"直达"服务器文件系统"——**攻击链极短、利用成本极低**，这是它被定为高危的原因

## 六、修复建议

| 层级 | 措施 |
|---|---|
| **升级（最直接）** | 将海洋 CMS 升级到官方已修复版本——此类 CMS 的公开漏洞通常都有对应补丁 |
| **代码（根治）** | 不把用户输入用作**变量名 / 模板名**；所有参数走白名单枚举 |
| 代码 | 禁用或限制危险函数（`eval`、`assert`、`preg_replace` 等）的能力 |
| 配置 | `disable_functions` 收敛可执行函数；Web 服务以低权限用户运行 |
| 配置 | 上传/数据目录禁止脚本执行，即使写入文件也无法解析 |
| 监测 | 对含 `{`、`}`、`eval`、`$_POST` 等特征的请求告警；关注 Web 目录异常新增文件 |

**优先级说明**：**"不再把用户输入当变量名解析"是根治**——只要保留这个能力，任何黑名单都会被绕过；**升级与收敛函数是纵深防御**。

## 七、延伸

**三条可以迁移到其他场景的判断**：

1. **看到"参数名可以被另一个参数控制"就该警觉**。这类"动态变量名"设计是注入的高发区（本例是 PHP 模板变量，Java 生态里对应 SpEL、OGNL 表达式注入）。
2. **越短的攻击链越危险**。这条链不需要账号、不需要上传点、不需要任何前置条件——**在风险评估里，"利用门槛低"本身就是提权因素**。
3. **归类要准，修复才对**。本实验最实用的教训已经在第一节说明：把 RCE 当成上传漏洞去修，等于没修。
