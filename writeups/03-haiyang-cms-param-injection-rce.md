# 海洋 CMS 影视站：参数注入导致的 RCE

| 项 | 内容 |
|---|---|
| 漏洞类型 | **参数注入 → 任意代码执行（RCE）** |
| 归属框架 | 绕过原理 —— 变量拼接 / 参数交叉引用 |
| 环境 | 授权靶场（海洋影视系统 / 海洋 CMS） |
| 工具 | 浏览器、Burp Suite、HackBar、WebShell 管理工具 |
| 复现日期 | 2025-06-27 |
| 风险等级 | **高危** —— 无需任何账号即可取得服务器控制权 |

---

## 一、现象

站点首页与搜索功能正常访问，无需登录。在搜索功能处提交一组**经过编排的参数**之后，服务端返回内容发生变化——不是报错，而是**像执行了一段代码**那样产生了输出。继续利用这个执行点写入脚本文件并访问，最终取得服务器控制权。

值得注意的是：整个过程中提交的**每一个参数单独看都毫无异常**——参数名普通、参数值里也没有明显的敏感词。

## 二、原理

### 2.1 成因：用户输入被当成"变量名"参与解析

海洋 CMS 的搜索功能在处理分页相关参数时，会把**用户传入的值当作模板变量名**参与字符串拼接与替换，而没有做白名单校验。这使得攻击者可以：

1. 用一个参数控制**另一个参数的名字**
2. 借助嵌套结构触发解析器的二次处理
3. 最终把**散落在多个参数里的片段拼成一段可执行代码**

**本质与 SSTI（服务端模板注入）同源**：用户输入进入了"模板 / 变量解析"环节，而不只是作为数据被处理。区别只在于这里有具体的 CMS 实现作为载体——同类设计在其他语言生态里对应表达式注入（如 Java 的 SpEL、OGNL）。

### 2.2 为什么每个参数看起来都无害

这是本篇最值得记的一点。这条利用**把必然会被 WAF 拦下的两个危险关键词，拆成多个无害碎片，分散到不同参数里**，再靠程序自身的变量替换机制把它们拼回完整形式。

于是出现了两层看到的东西完全不同：

| 观察者 | 看到的内容 |
|---|---|
| WAF / 参数级过滤 | 若干个普通字母片段，没有一个构成危险词 |
| 程序解析阶段 | 碎片按变量引用规则展开，拼回完整表达式 |

**这正是[绕过原理](../FRAMEWORK.md)的形态之一：过滤发生在字符串层（逐个参数检查字面内容），解析发生在语义层（跨参数展开后再解析），两者不一致处就是缝隙。**

把它放到同一原理的其他形态旁边看，会更清楚这只是同一件事的一种表达：

| 手法 | 过滤器看到的是 | 解析后变成 |
|---|---|---|
| 关键词双写（见 [04 篇](04-xss-labs-1-7.md)） | 中间夹了多余字符的字符串 | 过滤只替换一次，多余层被消掉、还原出关键词 |
| 命令执行变量拼接 | 若干变量赋值的普通片段 | shell 展开变量后组成完整命令 |
| **本篇：参数交叉引用** | 每个参数都是无害碎片 | 程序把碎片拼回完整表达式 |

> 三者都在利用同一件事：**被检查的字符串，不是最终被解析的东西。**

### 2.3 为什么归类必须搞清楚

原实验报告把这条归为**文件上传漏洞**。但从利用结构看，它自始至终**没有任何上传点**：走的是"参数被当模板表达式解析"这条链，与文件上传无关。

这不是措辞问题，它直接决定修复动作：

- 若按**上传漏洞**修 → 动作会落在"加后缀白名单、上传目录禁执行"。而**这套措施对这个漏洞完全无效**，因为根本不存在文件上传这个入口。
- 若按**参数注入 / 模板解析注入**修 → 动作才是"不把用户输入当变量名解析、收敛危险函数、升级到已修复版本"。**这才是对症的。**

**报漏洞时，"它属于哪一类"直接决定"它该怎么修"。归类错了，修复建议就会全错。**

## 三、复现

1. 访问目标站点，确认系统与版本
2. 定位搜索功能，用 Burp Suite 抓取一次正常的搜索请求，记录全部参数
3. 观察哪些参数之间存在引用关系（例如某个参数的值里出现了另一个参数的名字）——这是判断"参数被当变量名解析"的关键动作
4. 按引用关系编排一组参数提交，观察响应：**出现非预期的执行结果**，说明解析与拼接成立
5. 借此执行点写入一个**仅用于验证存在性**的最小内容文件（不含任何可用后门）
6. 访问该文件，确认返回的是执行结果而不是文件内容——这一步验证"能被解析"这条
7. 在 Web 根目录下确认落点

**关键判断点（脱敏）**

```
入口：      搜索接口的若干参数
要改的字段：<哪些参数、为什么是它们——写清"怎么从参数值里的互相引用的名字发现的">
观察到的现象：<响应出现非预期输出；后续访问写入的文件返回执行结果>
由此得出的结论：参数被当作变量名二次解析并执行
```

> **找到"要改哪个字段"的方法**：先正常操作一次，把请求参数全部列出，找其中**值里出现了别的参数名**的那些——这种"参数名出现在参数值里"的现象，就是变量引用机制的痕迹。

## 四、危害

- **远程代码执行（RCE）**：无需登录、无需任何前置权限，直接取得代码执行能力
- **服务器完全失陷**：可读写任意文件、执行系统命令
- **业务数据泄露**：配置文件中的数据库凭据、站点数据
- **横向渗透**：以该主机为跳板探测内网
- **攻击链极短**：从"一个搜索参数"直达"服务器文件系统"，无需账号、无需上传点、无需任何前置条件——**在风险评估里，"利用门槛低"本身就是提权因素**

## 五、修复

| 层级 | 措施 |
|---|---|
| **升级（最直接）** | 升级到官方已修复版本——此类 CMS 的公开漏洞通常已有对应补丁 |
| **代码（根治）** | 不把用户输入用作**变量名 / 模板名**；所有参数走白名单枚举 |
| 代码 | 收敛危险函数（动态执行类、可执行字符串的函数）的使用范围 |
| 配置 | 通过运行环境限制可执行函数；Web 服务以低权限用户运行 |
| 配置 | 数据与上传目录禁止脚本执行——即使写入文件也无法解析 |
| 监测 | 对含模板定界符、动态执行函数名、超参数字段的请求告警；关注 Web 目录异常新增文件 |

**哪一条更根本**：**"不再把用户输入当变量名解析"才是根治**——只要保留这个能力，任何黑名单都会被绕过（对照框架二：过滤挡不住解析层的重组）。升级与收敛函数属于纵深防御，能让已有漏洞更难被利用，但没有消除缺口的本质。

## 六、延伸

**三条能迁移到别处去的判断**：

1. **归类要准，修复才对。** 这是本篇最实用的教训：把 RCE 当成上传漏洞去修，等于没修。以后再遇到"这条该算哪一类"的犹豫时，先问一句：**按我给的归类，修复动作能不能真正拦住这次的利用路径？** 拦不住，说明归类错了。
2. **看到"参数名可以被另一个参数控制"就该警觉。** 这类"动态变量名"的设计是注入的高发区——因为它把"输入"从数据提升成了语法结构的一部分。这正好是框架二的核心形态：**一旦输入能影响解析过程而不只是被解析，字符串层与语义层就分家了。**
3. **越短的攻击链越危险。** 这条链不需要账号、不需要上传点、不需要任何前置条件。定级时，"利用门槛低"应该单独记一笔——**同样能拿 shell 的两个漏洞，需要一个账号的那个和不需要账号的那个，风险不是一个量级。**
