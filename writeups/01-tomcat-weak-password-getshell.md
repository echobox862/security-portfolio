# Tomcat 弱口令 && 后台 getshell

| 项 | 内容 |
|---|---|
| 漏洞类型 | 弱口令 + 任意文件部署（后台 getshell） |
| 归属框架 | getshell 三元组 —— WAR 部署路径 |
| 环境 | 授权靶场（Tomcat 管理后台） |
| 工具 | 浏览器、Burp Suite、WebShell 管理工具 |
| 复现日期 | 2025-06-25 |
| 风险等级 | **高危** —— 可直接取得服务器命令执行能力 |

> 靶场域名、账号与文件路径已脱敏。

---

## 一、现象

目标 Tomcat 的首页可正常访问。管理后台 `/manager/html` 用一组默认凭据即可登录，登录后可以把一个 WAR 包部署上去；部署完成后，访问包内脚本文件的路径，返回的是**脚本执行结果**而不是文件内容——由此取得服务器控制权限。

值得注意的一点：整条链上**没有一个"漏洞利用代码"**，全部动作都是管理后台的正常功能。

## 二、原理

### 2.1 这条链由两个独立缺陷叠加而成

**缺陷一：管理后台使用默认凭据**

Tomcat 的管理功能由 `manager` 应用提供，账号配置在 `conf/tomcat-users.xml`。较新版本该文件默认不配置任何账号（相关配置行保持注释），但历史版本、镜像模板或运维自行配置时，常保留出厂默认值。

这里要分清一件事：**弱口令的本质不是"密码太简单"，而是"默认值从未被修改"**。前者是人的选择问题，后者是配置管理问题——它属于安全配置错误（Security Misconfiguration）这一类，而不是"口令强度"这一类。这个区分会影响修复动作：改强密码只解决了一半，真正的修复是**不保留默认值、并且不把管理入口暴露出去**。

**缺陷二：Manager 的 deploy 功能把"上传能力"升级成了"代码执行能力"**

Manager 提供 Web 应用的部署/启动/停止，设计目的是方便运维发版。它接受 `.war` 包并自动解压到 `webapps` 目录部署；而 `.war` 内部可以放 `.jsp`，JSP 又是 Tomcat 正常解析的服务端脚本。

于是"上传一个包"在语义上等价于"在服务器上放了一个会被执行的脚本"。**部署功能本身是合规的管理功能，但它恰好满足了代码执行所需的全部条件。**

### 2.2 用 getshell 三元组复盘

| 条件 | 在本例中由谁满足 |
|---|---|
| 能写进去 | Manager 的 deploy 功能——本身就是为写文件设计的 |
| 能访问到 | WAR 解压到 `webapps`，应用名与文件名共同决定访问路径，路径可推导 |
| 能被解析 | 包内是 `.jsp`，由 Tomcat 自身解析 |

**三条全部天然满足。** 这就是为什么"后台弱口令"看起来只是个口令问题，实际后果却是服务器失陷——**它的危害不取决于口令有多弱，而取决于它打开了什么功能。**

## 三、复现

1. 访问目标首页，确认服务与版本
2. 访问管理界面 `/manager/html`，用默认凭据登录（登录成功说明缺陷一成立）
3. 将测试用脚本文件打包为 `.war`（内容用最小验证用途，不含任何可用后门）
4. 在管理界面找到 **WAR file to deploy** 位置，选择并部署
5. 部署完成后，按"包名 / 包内文件名"拼出访问路径并访问
6. **关键观察点**：页面返回的是脚本执行结果，而不是把文件当静态内容下载——这一步才真正验证了"能被解析"这条
7. 在文件系统中向上层目录回溯，定位到目标文件

**关键判断点（脱敏）**

```
入口：      管理后台的部署功能
路径规律：  <应用名>/<脚本名>.jsp —— 包名成为上下文路径，包内文件名成为访问名
验证方式：  访问该路径，看返回的是执行结果还是文件本身
```

> **「路径可知」这条值得单独记**：WAR 部署的访问路径是可以从包名和文件名直接推导出来的，不需要额外信息泄露。这是三元组里第 2 条被满足的方式；换成文件上传场景就未必这么顺——那时往往要靠报错、路径泄露或目录遍历去补这条。

## 四、危害

- **服务器完全失陷**：获得 Web 服务权限下的任意命令执行
- **数据泄露**：可读取配置文件（数据库连接串、密钥）与业务数据
- **横向渗透跳板**：以该主机为起点探测内网
- **追责困难**：操作全部通过管理后台的合规功能完成，日志里看起来像一次正常的应用部署

**利用前提清单**

- [x] 能写进去 —— Manager 的 deploy 功能
- [x] 能访问到 —— 解压到 `webapps`，路径可推导
- [x] 能被解析 —— `.jsp` 由 Tomcat 解析

## 五、修复

| 层级 | 措施 |
|---|---|
| **配置（最根本）** | 生产环境不部署 `manager` / `host-manager` 应用——用不到就删掉，攻击面直接消失 |
| **配置** | 管理后台不对外网开放，限制来源 IP；确需远程管理时走内网或跳板 |
| 配置 | 删除或禁用出厂默认账号；如必须保留，改为强密码 + 登录失败次数限制 |
| 运行 | Tomcat 以低权限用户运行，避免服务被拿下即等于主机沦陷 |
| 监测 | 关注 `webapps` 目录异常新增文件，以及管理后台的非预期部署请求 |

**哪一条更根本**：**"不暴露管理后台 + 不部署 manager 应用"是配置层措施，直接改变了能力边界**；而改强密码只是让第 1 条更难满足，第 2、3 条仍然完好——一旦凭据以别的方式泄露，整条链立刻恢复可用。所以加固的优先顺序是先收边界，再谈口令。

## 六、延伸

**弱口令本身不是一件独立的事，它的危害等于"它能打开的那个功能"的危害。** 同样是后台弱口令，后果可能完全不同：

- 打开的是**文件部署** → 直接 getshell（本例）
- 打开的是**文件管理** → 等价于任意文件上传，再走一遍三元组
- 打开的是**系统监控 / 日志查看** → 信息泄露，可能为下一步提供凭据或路径

所以评估这类漏洞时，问题不该停在"口令强度够不够"，而应该问：**这个后台能做什么？它做的那些事里，有几条能拼出完整链条？**

另外，这条链与本仓库的 [02 篇 Less 7](02-sqli-labs-less1-10.md)（`into outfile` 写文件）走的是**同一个三元组**：写入通道不同（一个是部署功能，一个是 SQL 写文件），但"能访问到 + 能被解析"这两条完全相同。把三元组记住，两条链的判断就是同一个。
