# CatfishCMS 水平越权：修改他人文章

| 项 | 内容 |
|---|---|
| 漏洞类型 | **水平越权（IDOR / BOLA）** |
| 目标 | CatfishCMS |
| 工具 | 浏览器、Burp Suite |
| 复现日期 | 2025-07-01 |
| 风险等级 | **中危**——可越权篡改他人数据；若推广到删除/发布接口，危害可进一步放大 |

## 一、现象

使用 A 账号发布的文章，可以被 B 账号（同为作者权限）通过修改请求中的文章 id **直接编辑并保存成功**——服务端返回成功，A 账号的文章内容确实被改动。

## 二、原理

### 2.1 缺了什么校验

系统做了两层校验，但**漏掉了最关键的一层**：

| 校验层 | 是否做了 | 说明 |
|---|---|---|
| **认证**：你有没有登录？ | ✅ 做了 | 未登录无法进入后台 |
| **功能授权**：你的角色能不能用"编辑文章"这个功能？ | ✅ 做了 | 两账号都是作者权限，都能进编辑页 |
| **对象授权**：**这篇文章是不是你的？** | ❌ **没做** | **漏洞就在这里** |

于是请求里的文章 id 成了唯一决定"编辑哪篇"的依据——而 **id 由客户端提交**。把 id 改成别人的，服务端就照做。

### 2.2 为什么实验要用"两个账号"

**这是本实验设计上最讲究的一点**，也值得单独记住：

用**两个同权限账号**（test11 被越权、test22 实施越权）才能证明：

- 如果只用低权限账号去操作高权限功能 → 那是**垂直越权**（权限提升）
- **用同权限账号 A 去操作账号 B 的数据 → 才是水平越权**（平行权限跨越）

**换句话说：验证水平越权必须准备两个"平级"账号，否则证明不了"越权"这件事本身。** 这是写测试用例时的一个硬要求。

### 2.3 这是一类"工具扫不出来"的漏洞

自动化扫描器通常识别不了它——因为：

- 请求**语法完全合法**：参数名正常、值正常、没有特殊字符
- 返回**状态码正常**：`200`，没有报错
- **唯一的问题是"语义"错了**：这个操作不该被允许

> **判断依据**：这类漏洞只能靠**人工理解业务规则**发现——"这个接口应该只允许操作自己的数据吗？"这个问题，扫描器不会问。
> **与本项目其他实验对照**：业务逻辑类漏洞（重复注册、刷积分、序列号绕过）和本条是同一性质——**它们不破坏代码，只破坏规则**。

## 三、复现步骤

1. 访问目标站点，确认应用为 **CatfishCMS**
2. 准备**两个作者权限账号**（记为 A、B）
3. 用 **A 账号**登录，撰写并发布一篇文章
4. 在"所有文章"列表中打开这篇文章，**记录其文章 id**（可从编辑链接或请求参数中获得）
5. 用 **B 账号**登录，同样撰写并发布一篇自己的文章
6. 在"所有文章"中选择**自己那篇**点击编辑，同时用 Burp Suite **抓包**
7. 在请求中**把文章 id 改成第 4 步记录的 A 的文章 id**，放行请求
8. 回到 A 账号查看，**文章内容已被修改**——越权成立

**关键请求（脱敏）**

```
POST /admin/article/edit  HTTP/1.1
Host: <target>

id=<A 账号的文章 id>&title=...&content=...
```

> **要改的字段就是那个 id**。判断"改哪个字段"的方法：先正常提交一次，对比请求参数，找到标识对象的那个值。

## 四、危害

- **数据完整性被破坏**：可任意篡改他人发布的文章、简介、状态
- **可类推到其他接口**：如果编辑接口没做归属校验，那么**删除、置顶、发布、下架**等接口大概率也没有——**风险面会随地扩大**
- **配合批量遍历**：id 通常是连续数字，改一个 id 的脚本化处理就是"批量篡改"
- **追责困难**：操作是在受害者账号的内容上发生的，日志里看到的是"某人编辑了某文章"，容易造成责任混淆
- 若该系统存在更高价值对象（订单、资料、私信），越权读取会造成**敏感数据泄露**

## 五、修复建议

| 层级 | 措施 |
|---|---|
| **代码（根治）** | 所有涉及对象的操作，服务端**必须校验对象归属**：`WHERE id = ? AND author_id = <当前登录用户 id>`，让"越权"在 SQL 层面直接查不到数据 |
| 代码 | **不要信任客户端提交的对象 id**作为授权依据——id 只用于定位对象，授权必须来自服务端会话 |
| 设计 | 对象 id 改用 **UUID / 雪花 ID**，降低可枚举性（**这只是提高难度，不能替代归属校验**） |
| 设计 | 建立统一的授权中间件，避免各接口各写一套校验而漏掉 |
| 监测 | 记录"操作人 / 被操作对象 / 对象属主"三者的不一致事件并告警——**这是发现越权最直接的信号** |

**优先级说明**：**对象的归属校验必须落到数据查询条件里**，而不是先查出数据再在代码里 if 判断——前者从机制上杜绝，后者只要漏一个分支就失效。

## 六、延伸

**三条可迁移的判断**：

1. **认证 ≠ 授权**。登录了不代表有权做任何事；功能授权（能不能用这个功能）也不等于对象授权（能不能操作这条数据）。**三者要分开测、分开修。**
2. **凡是"改个 id 就能换对象"的接口，都要试一遍**。这是发现越权最省力的路径：找到任何一个含对象 id 的请求，把 id 换成别人的（或换成一个不存在的），观察响应差异。
3. **术语对齐会让沟通更准确**。这类漏洞在行业里也常被称作 **IDOR（不安全的直接对象引用）** 或 **BOLA（对象级授权失效）**，并且它对应 **OWASP Top 10:2025 的 A01「失效的访问控制」——已连续多版排在第 1 位**，是当前最普遍的应用安全风险之一。

> **顺带记录一个现代变化**：OWASP Top 10:2025 中，**SSRF 已不再独立成类，被并入 A01 失效的访问控制**。也就是说，"服务器能访问什么"和"用户能访问什么"现在被放在同一个大类下讨论——**越权类问题的重要性比几年前更被强调**。
