# CatfishCMS 水平越权：修改他人文章

| 项 | 内容 |
|---|---|
| 漏洞类型 | **水平越权（IDOR / BOLA）** |
| 归属框架 | 两条框架均不适用 —— 属授权类缺陷，说明见第二节 |
| 环境 | 授权靶场（CatfishCMS） |
| 工具 | 浏览器、Burp Suite |
| 复现日期 | 2025-07-01 |
| 风险等级 | **中危** —— 可越权篡改他人数据；若同类缺陷存在于删除 / 发布 / 下架接口，危害可进一步放大 |

> 靶场账号与地址已脱敏，两个账号在下文记为 A、B。

---

## 一、现象

用 A 账号发布的文章，可以被 B 账号（**同为作者权限**）通过修改请求中的文章 id **直接编辑并保存成功**。服务端返回成功，回到 A 账号查看时，文章内容确实被改动。

整个过程里，请求没有任何异常特征：参数名正常、参数值正常、没有特殊字符、没有报错。

## 二、原理

### 2.1 缺的是"对象归属"这一层校验

系统做了两层校验，但漏掉了最关键的一层：

| 校验层 | 是否做了 | 说明 |
|---|---|---|
| **认证** —— 有没有登录？ | ✅ 做了 | 未登录无法进入后台 |
| **功能授权** —— 这个角色能不能用"编辑文章"功能？ | ✅ 做了 | 两个账号都是作者权限，都能进编辑页 |
| **对象授权** —— **这篇文章是不是你的？** | ❌ **没做** | **漏洞就在这里** |

于是请求里的文章 id 成了唯一决定"编辑哪一篇"的依据——而 **id 由客户端提交**。把 id 改成别人的，服务端就照做。

**这三层必须分开看待**：登录了不代表有权做任何事（认证 ≠ 授权）；能用某个功能，不代表能用在该对象上（功能授权 ≠ 对象授权）。**三层要分开测、分开修**——只在其中一层加校验，另外两层仍然是缺口。

### 2.2 为什么它不归入那两条框架

本仓库的[两条框架](../FRAMEWORK.md)都是围绕**输入的解析差异**展开的：输入被当代码执行、或过滤与解析不一致。而这类漏洞里，**输入从头到尾都合法、也被正确解析**——参数没有被当代码，过滤也没有被绕过。

它坏在**业务规则**上：请求在语法与解析上都没问题，**唯一错误的是"这个操作本不该被允许"**。所以它需要单独一类判断，不能硬套框架。

**与之同类的是业务逻辑类缺陷**（重复注册、刷积分、兑换规则绕过等）：它们不破坏代码，只破坏规则。本仓库暂时没有为这一类建框架——如果以后这类笔记多了，值得单独总结一条。

### 2.3 为什么验证它必须用两个"平级"账号

这是本实验设计上最讲究的一点，也是写测试用例时的硬要求：

- 用**低权限账号**去操作**高权限功能** → 那是**垂直越权**（权限提升）
- 用**同权限账号 A** 去操作**账号 B 的数据** → 才是**水平越权**（平行权限跨越）

**换句话说：验证水平越权必须准备两个平级的账号，否则证明不了"越权"这件事本身。** 用一个管理员账号去改另一个管理员的数据，虽然也能说明问题，但无法排除"是权限配置本身给了这个能力"，结论就不干净。

### 2.4 这类漏洞为什么自动化扫描器扫不出来

因为它在所有"机器可判"的维度上都是正常的：

- 请求**语法完全合法**：参数名正常、值正常、没有特殊字符
- 响应**状态码正常**：返回成功，没有报错
- **唯一错的是语义**：这个操作不该被允许

> **判断依据**：这类漏洞只能靠人工理解业务规则来发现。扫描器不会问"这个接口应该只允许操作自己的数据吗"——**它只会问"这个请求有没有异常特征"。**

## 三、复现

1. 访问目标站点，确认应用类型
2. 准备**两个同权限账号**（记为 A、B）
3. 用 **A 账号**登录，撰写并发布一篇文章
4. 在文章列表打开这篇文章，**记录它的对象 id**（可从编辑链接或请求参数中获得）
5. 用 **B 账号**登录，同样发布一篇自己的文章
6. 在列表中选择**自己那篇**点击编辑，同时用 Burp Suite **抓包**
7. 把请求中的对象 id 改成第 4 步记录的、A 那篇的 id，放行请求
8. 回到 A 账号查看：**文章内容已被修改**——越权成立

**关键判断点（脱敏）**

```
入口：      <文章编辑接口>
要改的字段：请求里标识对象的那个 id
怎么找到它：先正常提交一次，对比请求参数，找"值随对象变化"的那一个
对比方法：  同一个请求、只改 id，用 B 的会话发给 A 的对象
观察到的现象：服务端返回成功，A 的对象内容被改动
```

> **找到"要改哪个字段"的方法**：不要凭经验猜字段名。先正常操作一次，把请求参数全部列出，逐一对比——**改动对象后值跟着变的那一个，就是标识对象的字段。** 这个方法对所有越权测试都通用。

## 四、危害

- **数据完整性被破坏**：可任意篡改他人发布的内容、简介、状态
- **可类推到其他接口**：如果编辑接口没做归属校验，那么**删除、置顶、发布、下架**等同类接口大概率也没有——**风险面会成片扩大，而不是单点**
- **可脚本化批量利用**：对象 id 通常是连续数字，把改 id 的过程脚本化就是批量篡改
- **可造成敏感数据泄露**：若系统中存在价值更高的对象（订单、资料、私信），把"改"换成"读"即可越权获取
- **追责困难**：操作落在受害者账号的内容上，日志里只看到"某人编辑了某篇文章"，容易造成责任混淆

**利用前提清单**

- [x] 有可用的普通账号（本例两个同权限账号）
- [x] 请求中存在标识对象的字段
- [x] 服务端不校验该对象与当前登录用户的归属关系

## 五、修复

| 层级 | 措施 |
|---|---|
| **代码（根治）** | 所有涉及对象的操作，服务端**必须校验对象归属**：把归属条件写进数据查询条件里（"这条数据且属于我"），让越权在查询阶段就查不到数据 |
| 代码 | **不要信任客户端提交的对象 id 作为授权依据**——id 只用于定位对象，授权必须来自服务端会话 |
| 设计 | 对象 id 改用不可预测的形式（UUID / 雪花 ID），降低可枚举性。**这只是提高门槛，不能替代归属校验** |
| 设计 | 建立统一的授权中间件，避免各接口各写一套校验而漏掉某个 |
| 监测 | 记录"操作人 / 被操作对象 / 对象属主"三者不一致的事件并告警——**这是发现越权最直接的信号** |

**哪一条更根本**：**归属校验必须落到数据查询条件里**，而不是先查出数据、再在代码里用条件判断过滤。前者从机制上杜绝（查不到就是查不到），后者只要漏掉一个分支就失效——而这类漏洞恰恰就是"漏了一个分支"造成的。

## 六、延伸

**三条可迁移的判断**：

1. **认证 ≠ 授权，功能授权 ≠ 对象授权。** 三者要分开测、分开修。看到一个接口时，依次问三个问题：**要不要登录？这个角色能不能用这个功能？这条数据是不是他的？** 前两个通常都有答案，第三个最常被漏掉。
2. **凡是"改个 id 就能换对象"的接口，都要试一遍。** 这是发现越权最省力的路径：找到任何含对象 id 的请求，把它换成别人的（或换成一个不存在的），观察响应差异。**换成不存在的 id 也能看出问题**——如果服务端返回"对象不存在"而不是"无权限"，说明它压根没做归属判断。
3. **术语对齐会让沟通更准确。** 这类漏洞在行业里也常被称为 **IDOR（不安全的直接对象引用）** 或 **BOLA（对象级授权失效）**，对应 **OWASP Top 10:2025 的 A01「失效的访问控制」**，已连续多版排在第 1 位。

> **顺带记录一个版本变化**：在 OWASP Top 10:2025 中，**SSRF 已不再独立成类，被并入 A01 失效的访问控制**——也就是说，"服务器能访问什么"和"用户能访问什么"现在放在同一个大类下讨论。
