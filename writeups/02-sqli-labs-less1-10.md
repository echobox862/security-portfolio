## 一、关卡全景：这一套练习真正在讲什么

sqli-labs 的 Less 1–10 表面是十个独立关卡，实际上是**一条技术演进线**——**随着"回显越来越少"，注入手法必须逐级升级**：

| 关卡 | 闭合方式 | 注入类型 | 这一关新增的能力要求 |
|---|---|---|---|
| Less 1 | `'` | 联合查询（有回显） | 判断闭合符、定列数、定显示位 |
| Less 2 | 无（数字型） | 联合查询 | 识别"参数没被引号包裹"的情况 |
| Less 3 | `')` | 联合查询 | 遇到括号+引号的组合闭合 |
| Less 4 | `")` | 联合查询 | 闭合符换成双引号 |
| Less 5 | `'` | **报错注入** | 页面不回显数据，只能靠报错把数据"挤"出来 |
| Less 6 | `"` | 报错注入 | 同上，换闭合符 |
| Less 7 | `'))` | **写文件 getshell** | 不回显，用 `into outfile` 直接落地 webshell |
| Less 8 | `'` | **布尔盲注** | 连报错都没有，只能靠页面"正常/异常"猜 |
| Less 9 | `'` | **时间盲注** | 页面连真假都无差异，只能靠响应延时判断 |
| Less 10 | `"` | 时间盲注 | 同上，换闭合符 |

**这条主线本身就是最值得记住的东西**：**攻击者能获取的信息通道是逐级收窄的——数据回显 → 报错信息 → 页面布尔差异 → 响应时间差异。手法的复杂度完全由"还剩哪条通道"决定。**

## 二、第一梯队：有回显的联合查询（Less 1–4）

### 2.1 通用流程（Less 1 完整走一遍）

| 步骤 | 做了什么 | 为什么这么做 |
|---|---|---|
| ① 探闭合符 | 在 `id` 后加单引号，页面报错 | 报错说明**参数被拼进了 SQL 且引号被破坏**——证明"参数可控 + 带入查询"两个条件成立 |
| ② 验证可控性 | 试 `and 1=1` 与 `and 1=2`，前者正常、后者异常 | **真假对比法**：`1=1` 恒真、`1=2` 恒假，两次结果不同就说明参数参与了逻辑判断 |
| ③ 定列数 | `order by 10` 报错 → 二分法逐步逼近 → 到 3 时正常 | `order by` 后面的列序号超过实际列数会报错，**用"越界报错"反推列数** |
| ④ 定显示位 | `union select 1,2,3`，并把 `id=1` 改成 `-1` | 列数必须一致 union 才成立；**把前置查询置空，页面显示的才是 union 的结果** |
| ⑤ 取数据 | 在显示位放 `version()` / `database()` / `user()`，再逐层读 `information_schema` | 先确认自己站在哪个库、什么权限，再按"库 → 表 → 字段 → 数据"逐层剥开 |

**本关踩到的一个实际坑**：payload 里用 `#` 注释时被忽略，改成 URL 编码 `%23` 才生效。

> **这个坑很有代表性**：`#` 在 URL 中是片段标识符，浏览器不会把它发给服务器。**凡是"payload 明明对但打不通"的情况，先检查特殊字符有没有正确编码**（`#` → `%23`、空格 → `%20`）。

最终 payload（Less 1）：

```
?id=-1%27union%20select%201,2,3%23
```

### 2.2 四个关卡的区别只在"闭合符"

| 关卡 | 参数在 SQL 中的形态 | 试出来的闭合方式 |
|---|---|---|
| Less 1 | `WHERE id = '$id'` | `'` |
| Less 2 | `WHERE id = $id` | **无引号包裹**（所以加单引号会报错，但 `and 1=1` 直接生效） |
| Less 3 | `WHERE id = ('$id')` | `')` |
| Less 4 | `WHERE id = ("$id")` | `")` |

**Less 2 的识别要点**：加单引号无效、去掉单引号反而 `and 1=1` 生效——**说明参数是数字型，根本不需要闭合任何引号**。

**Less 3 / Less 4 的识别要点**：先试单引号、再试括号，逐一排除；**Less 4 的关键动作是"把 Less 3 的单引号换成双引号"** ——这说明两个关卡的业务代码结构相同，只有引号类型不同。

> **方法论意义**：这四个关卡合起来教的是"**排查闭合符的标准顺序**"——单引号 → 括号 → 双引号 → 组合。真实环境中遇到注入点时，也是按这个顺序试。

## 三、第二梯队：报错注入（Less 5–6）

**变化**：`union select` 执行成功，但结果**不显示在页面上**。这说明查询确实被执行了，只是没有回显位。

**手法**：改用 **`floor()` 报错注入**——构造一个必然产生错误的表达式，**让数据库把我们要的数据写进错误信息里返回**。

**本关踩到的第二个坑**：报错信息提示"字符超过 64 位"。

> **这就是 `group_concat` 的长度限制**：`group_concat_max_len` 默认 1024 字节，超出的部分会被**静默截断**，而某些报错注入的构造还会额外触发报错的长度上限。
> **解决办法**：放弃一次读全部，改用 `limit 0,1`、`limit 1,1` **一次读一行**，逐行取回。

**这是本实验里最有价值的一处实践认知**：**"一次读全部"往往只是理想情况，真实注入必须处理长度截断、超时、被 WAF 拦等限制，分段读取是常态。**

拿到数据后，与联合查询一样逐层推进：`database()` / `user()` / `version()` → 表名 → `users` 表列名 → 逐行读出用户名与密码。

## 四、第三梯队：写文件直接 getshell（Less 7）★

**变化**：`'))` 闭合，且同样不回显——但这一关只需要"能执行"，不需要"能看到"。

**思路**：既然能控制 SQL 语句，就用 `into outfile` **把一句话木马写到 Web 目录**，然后用 WebShell 工具连接。

### 4.1 两次尝试，暴露了一个关键限制

**第一次：想写 521.php 失败。** 检查 `secure_file_priv` 配置后没有发现问题。

**第二次：改用相对路径穿越，成功了。** 把写入路径从"MySQL 数据目录"改成"用 `..\..\` 跳出去再到 Web 根目录"：

```
?id=3%27))%20union%20select%201,2,3%20into%20outfile%20%22D:\\phpstudy\\PHPTutorial\\MySQL\\data\\..\\..\\WWW\\520.php%22%23
```

写入成功后，用同样的方式把木马内容写进去：

```
?id=-3%27))%20union%20select%201,%27<无害内容>%27,3%20into%20outfile%20%22D:\\phpstudy\\PHPTutorial\\MySQL\\data\\..\\..\\WWW\\5.php%22%23
```

> **说明**：原实验中该位置放的是最简命令行 shell，为便于公开此处替换为无害内容。**理解结构即可**——真正要记住的是路径怎么写、为什么能跳出去。

### 4.2 为什么"路径穿越"能绕过限制（本实验最值得记住的技术点）

先补一层背景：**MySQL 5.7 起引入、8.0 起严格执行 `secure_file_priv`**，它把 `LOAD_FILE()` 与 `SELECT ... INTO OUTFILE` 的可访问范围**限制在指定目录内**；8.0 默认值是 `NULL`，即**完全禁止**这两个操作。

本例中该变量并非 NULL（所以能写），但**可写范围被限制在 MySQL 数据目录**——这就解释了第一次为什么写不到 Web 目录。

**关键点在于**：路径限制通常只做"字符串前缀判断"，而**没有对路径做规范化（没有消解 `..`）**。于是：

```
D:\phpstudy\PHPTutorial\MySQL\data\..\..\WWW\520.php
└──────── 被允许的前缀 ────────┘  └─ 实际落点：phpstudy\WWW\520.php ─┘
```

**"字符串上看起来在允许目录里，解析后实际落在 Web 根目录"** —— 这就是绕过成立的原因。

> **这个原理与注入类漏洞的绕过是同一个套路**：**限制发生在字符串层，解析发生在语义层，两者不一致处就是缝隙。**
> 同一原理的其他形态：命令执行里的 `$IFS`、文件上传里的尾部点/空格、URL 里的 `%00`。

**补充提示**：如果目标是 MySQL 8 且 `secure_file_priv` 为默认的 `NULL`，这条链**走不通**，需要另找写入通道（如日志文件注入、或借助文件上传点）。

### 4.3 为什么必须知道"绝对路径"

写文件前需要知道目标路径。本实验用 `@@datadir`（数据库数据目录）和 `@@basedir`（安装目录）查路径；因为 Less 7 不回显，**回到前面的回显关卡去查**，拿到路径后回到 Less 7 使用。

> **这体现了"漏洞利用常常需要跨点组合"**：单点不回显不要紧，只要**同一个系统上还有另一个能回显的注入点**，就能借它查信息。真实渗透里这类"借 A 点的回显读 B 点的数据"非常常见。

## 五、第四梯队：布尔盲注（Less 8）

**变化**：连报错信息都没有了，页面只有"正常 / 异常"两种状态。

**手法**：把"猜数据"变成一系列判断题，**靠二分法把猜测次数压到对数级**。

完整流程：

1. **猜长度**：`length(database()) > 5`、`> 8`…… 二分法逼近，得出库名长度为 8
2. **猜内容**：用 `ascii(substr(database(),1,1)) > 100` 这类判断，**逐位二分出 ASCII 码**，再对照字符表得出字符
3. **猜库名**：首字母为 `s`…… 类推得到库名
4. **猜表**：先猜各表名长度（得出 6、8、7、5），再逐字猜出表名
5. **猜字段**：逐字猜出 `users` 表的列名
6. **猜数据**：同样的方法读出用户名与密码

> **为什么要 "先猜长度再猜内容"**：不知道长度就无法确定 `substr` 的循环边界；先用二分法把长度定下来，后面每一位的猜测才有明确终点。**这是盲注的标准作业顺序。**
>
> **二分法不只是"更快的技巧"，它是盲注能否在可接受时间内跑完的前提**——逐字符线性猜测的请求数量会随数据量迅速膨胀，而二分法把每一位的猜测次数压到对数级。这也是自动化工具（如 SQLMap）内部必须做的优化。

## 六、第五梯队：时间盲注（Less 9–10）

**变化**：页面连"正常/异常"都没有区分了——**唯一的输出通道只剩"响应花了多久"**。

**手法**：把判断题的结果编码为**时间**。用 `sleep()` 做延时：

```
?id=1%27and%20If(ascii(substr(database(),1,1))=115,1,sleep(5))--+
```

**读法**：如果条件成立 → 立即返回；如果条件不成立 → 卡 5 秒。**靠"有没有卡 5 秒"判断真假。**

逐位推进即可猜出全部数据：

- 得出库名 `security`
- 猜表：逐个表名、逐位判断，得到 `emails`、`referers`、`uagents`、`users`
- 再猜 `users` 表的列名与 `username` / `password` 的内容

**Less 10 与 Less 9 的唯一区别**：闭合符从单引号变成双引号。

> **补充**：除了 `sleep()`，还可以用 `BENCHMARK()` 制造计算耗时——**当目标环境禁用了 `sleep` 或它被 WAF 拦截时，这是备选方案**。

## 七、实验结果总结

通过本次 sqli-labs 10 个关卡的练习，完整走通了 SQL 注入的五种技术形态：

| 能力 | 覆盖关卡 | 关键产出 |
|---|---|---|
| 联合查询注入 | Less 1–4 | 定列数、定显示位、逐层读 `information_schema` |
| 报错注入 | Less 5–6 | 处理 `group_concat` 长度截断，改为分段读取 |
| 写入文件 getshell | Less 7 | 用 `@@datadir` / `@@basedir` 定位路径，`into outfile` 落地木马 |
| 布尔盲注 | Less 8 | 二分法猜长度与逐字符 ASCII |
| 时间盲注 | Less 9–10 | 用 `sleep()` 把布尔结果编码为响应延时 |

## 八、危害

- **数据库层面**：可读取任意库表与字段，包括用户凭据、业务数据
- **系统层面**：配合 `into outfile` 可写入文件 → 取得服务器命令执行能力
- **权限层面**：`load_file()` 可读取服务器文件（如有 FILE 权限且 `secure_file_priv` 允许）
- 本例中完整读出了用户表数据，并成功写入文件取得控制权——**证明了从"一个可控参数"到"服务器失陷"的完整链路**

## 九、修复建议

| 层级 | 措施 |
|---|---|
| **代码（根治）** | 全部数据访问改用**参数化查询 / 预编译**，从机制上消除"拼接" |
| 代码 | 输入做类型与格式校验（如 `id` 必须为整数则强制转换） |
| 配置 | 数据库账号遵循最小权限：业务账号不给 `FILE` 权限 |
| 配置 | `secure_file_priv` 设为其真正的默认值 `NULL`，彻底关闭导入导出 |
| 配置 | 关闭详细报错回显（`display_errors`），统一错误页面——**这是掐断"报错注入"整条通道的关键** |
| 监测 | 对含 SQL 关键字、异常编码（`%27`、`%23`）、超长/畸形参数的请求告警 |

## 十、延伸

**这套练习最该带走的三条**：

1. **注入的判定不依赖回显**。有回显用联合查询，没回显用报错，连报错都没有就用布尔或时间——**"没有回显"不等于"没有漏洞"，只是换了通道**。
2. **长度限制与分段读取是常态**。`group_concat` 会截断、盲注要考虑请求量——**真实注入几乎总要在"限制"里工作**。
3. **写入文件类操作必须先确认三个前提**：`FILE` 权限、`secure_file_priv` 允许的目录、目标目录对数据库进程可写。**任一条不满足，payload 再对也写不进去**——这正是本实验 Less 7 第一次失败的原因，也是我认为最值得记的一处实战经验。
