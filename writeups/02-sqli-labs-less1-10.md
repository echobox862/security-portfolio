# sqli-labs Less 1–10：同一套注入原理的五种取数通道

| 项 | 内容 |
|---|---|
| 漏洞类型 | SQL 注入（联合查询 / 报错 / 布尔盲注 / 时间盲注 / 写入文件） |
| 归属框架 | getshell 三元组（写入文件路径）· 绕过原理（路径穿越形态） |
| 环境 | sqli-labs 靶场（MySQL） |
| 工具 | 浏览器、Burp Suite、sqlmap、WebShell 管理工具 |
| 复现日期 | 2025-06-26 |
| 风险等级 | **高危** —— 可读全库数据，并可通过写文件取得命令执行 |

> 靶场路径、账号与提取到的数据均已脱敏。

---

## 一、现象

一个 `id` 参数即可读到数据库里的任意内容。但十道关卡的表现并不相同：有的直接把数据显示在页面上，有的只报错，有的什么都不显示、只能靠页面状态差别判断，最后一关连状态差别都没有、只能靠响应快慢判断。

**这说明一件事：漏洞是否成立，与页面有没有"回显"无关。** 页面输出只是取数的一条通道；通道消失了，只要参数可控，注入依然成立，只是要换一条通道。

## 二、原理

### 2.1 十道关卡的实质：一条"信息通道逐级收窄"的线

| 梯队 | 关卡 | 闭合方式 | 还剩哪条通道 | 对该关的能力要求 |
|---|---|---|---|---|
| 有回显 | Less 1–4 | 单引号 / 无引号 / 括号加单引号 / 括号加双引号 | 数据直接回显 | 探闭合符、定列数、定显示位 |
| 报错 | Less 5–6 | 单引号 / 双引号 | 报错信息 | 把数据"塞进"报错内容里 |
| 写文件 | Less 7 | 括号加单引号 | 不需要回显，只需要能执行 | 定位绝对路径 + 满足写入前提 |
| 布尔盲注 | Less 8 | 单引号 | 页面正常 / 异常 | 把取数变成一系列判断题 |
| 时间盲注 | Less 9–10 | 单引号 / 双引号 | 响应耗时 | 把判断结果编码为时间 |

**这条线本身比任何单个手法都重要**：通道从"数据回显 → 报错 → 布尔状态 → 响应时间"逐级消失，而手法的复杂度完全由"还剩哪条通道"决定。反过来看，**防御者只需要掐断全部通道**——尤其是"关闭详细报错回显"，一刀就能砍掉整个报错梯队。

### 2.2 为什么这些通道存在

它们的成因是同一个：**参数被拼进 SQL 语句字符串，而没有走参数化查询**。一旦数据进入了字符串拼接这一步，输入就不再是"数据"，而会被数据库当"语句的一部分"解析——**这属于[绕过原理](../FRAMEWORK.md)描述的那类问题：字符串层与语义层不一致**。

不同通道的差别只在于**数据库把结果送到了哪里**：

| 通道 | 数据库把结果送到哪 |
|---|---|
| 联合查询 | 送到正常的结果集里，随页面输出 |
| 报错注入 | 送到错误信息里（借必然失败的表达式把数据带出） |
| 布尔盲注 | 送到"真假"这个二元结果里 |
| 时间盲注 | 送到"执行耗时"里（用条件决定要不要等待） |

### 2.3 写文件那条链为什么要单独看

Less 7 与前几关不同：它**不需要"看到"任何数据，只需要"能执行"**。所以它归到的是另一条框架——[getshell 三元组](../FRAMEWORK.md)：写入能力来自 SQL 的写文件语法，访问能力靠"路径写到 Web 根目录"来满足，解析能力靠"写入的是服务端脚本"来满足。

而它满足"能访问到"的方式，恰好又是绕过原理的一个实例：**用相对路径跳目录**，让路径字符串看起来仍在允许目录内，实际落点却在 Web 根下。这一节的细节见 3.4。

## 三、复现

### 3.1 通用判定顺序（Less 1 完整走一遍）

| 步骤 | 动作 | 观察点与判断 |
|---|---|---|
| ① 探闭合 | 在参数值后追加一个引号类符号 | 页面报错 → 参数确实进入了 SQL，且这个符号破坏了原有语法 |
| ② 验证可控 | 提交"恒真"和"恒假"两种条件各一次 | 两次结果不同 → 参数参与了逻辑判断（这就是后面盲注的基础） |
| ③ 定列数 | 用排序序号逐次试探（先试一个偏大的值，再二分逼近） | 序号超过实际列数时报错 → 反推出真实列数 |
| ④ 定显示位 | 用联合查询占位对齐列数，并把前置查询置为不存在的值 | 占位内容出现在页面上 → 该位置可回显，是后续取数的入口 |
| ⑤ 取数 | 先在显示位取当前库名、用户名、版本，再逐层查表名、列名、数据 | 先确认"站在哪个库、什么权限"，再按"库 → 表 → 字段 → 数据"逐层剥开 |

**第 ④ 步的原理值得记牢**：联合查询要求前后列数一致；把前置查询置成不存在的值，是为了让页面显示的**只有**后半段的结果。这两点是"有回显注入"能否取到数的关键，和 payload 长什么样无关。

**本关踩到的坑**：注释符最初不生效，原因是该字符在 URL 里有特殊含义、被浏览器当成片段标识符截掉了，**必须先做 URL 编码再发**。

> 这个坑的通用价值：**凡是"payload 逻辑正确但打不通"的情况，先怀疑特殊字符的编码**——注释符、空格、井号、加号在 URL 里都有额外含义。这属于框架二里"编码类"的差异：过滤器或传输层看到的字符串，和到达服务端解析的字符串，不是同一个。

### 3.2 四个关卡的差别只在"参数在 SQL 里的位置"

| 关卡 | 参数在语句中的形态 | 试探出来的闭合方式 |
|---|---|---|
| Less 1 | 被单引号包裹 | 单引号 |
| Less 2 | 不被引号包裹（数字型） | 无 |
| Less 3 | 被括号加单引号包裹 | 括号加单引号 |
| Less 4 | 被括号加双引号包裹 | 括号加双引号 |

**识别要点**：Less 2 加引号无效、去掉引号反而让条件判断生效，说明参数是数字型、根本不需要闭合任何引号；Less 3 与 Less 4 的差别只是引号类型，说明两者代码结构相同。

> **能带走的是"排查闭合符的顺序"：单引号 → 括号 → 双引号 → 组合。** 真实环境遇到注入点也是按这个顺序试，而不是记住某关用哪个符号。

### 3.3 报错梯队：页面不显示数据，但不显示"错误"

**变化**：联合查询能执行成功，结果却不出现在页面上。

**思路**：数据库在报错时会把出错表达式的内容带进错误信息。所以构造一个必然失败的表达式，把想读的数据拼进去，数据就会随报错一起返回。

**本关踩到的坑**：报错提示内容超长。原因是聚合函数拼接结果有长度上限，超出的部分被**静默截断**，而某些报错构造本身还有额外的长度限制。

**处理**：放弃"一次读全部"，改成按行读取（每次只取一条记录），逐行拼回完整结果。

> **这是本篇最有实用价值的一处认知**：一次读全只存在于理想情况。真实注入总要在长度截断、超时、被 WAF 拦这些限制里工作，**分段读取是常态而不是退路**。
> 顺带一个可迁移的判断：**"一次拿到全部"的需求本身就值得怀疑**——凡是聚合输出，都要先想它的上限在哪里。

### 3.4 写文件梯队：从"能读到"到"能执行"

这一关闭合符是"括号加单引号"，页面同样不回显——但它**不需要回显**，只需要数据库能执行写文件操作。

**思路**：既然能控制语句，就用写文件语法把服务端脚本写到 Web 根目录，然后访问它。

**第一次尝试失败**：直接写目标文件不成功，检查配置变量也没发现问题。
**第二次尝试成功**：把写入路径改为"从数据目录用 `..\` 跳出去，再到 Web 根目录"。

**为什么路径穿越能成立**——这是本篇最值得记的技术点：

先补背景：MySQL 较新版本会用一个配置变量把文件读写限制在指定目录内；该变量取默认值时，这两个操作**被完全禁止**。本实验环境中它并非默认值，所以能写，但**可写范围被限制在数据目录**——这就解释了第一次为什么写不到 Web 目录。

**关键在于**：路径限制通常只做"字符串前缀判断"，**没有对路径做规范化（没有消解 `..`）**。于是路径字符串在字面上仍以允许目录开头，前缀检查通过；而文件系统在解析时把 `..` 消解掉，实际落点跑到了允许目录之外。

```
<允许目录>/<二级目录>/../../<Web 根>/<文件名>
└─────── 字符串上是允许的前缀 ───────┘   └─ 实际落点 ─┘
```

**"字符串上看起来在允许目录里，解析后实际落在 Web 根目录"** —— 这正是框架二的标准形态：限制发生在字符串层，解析发生在语义层，两者不一致处就是缝隙。

> 同一形态的其他例子：命令执行里用变量拼接绕过关键字过滤、文件上传里用尾部点或空格绕过后缀判断、URL 里用空字节截断绕过扩展名检查。手法各不相同，原理是同一个。

**补充判断**：如果目标用的是较新版本且配置变量保持默认值，这条链**走不通**——这时不该硬试，而要去找别的写入通道（日志文件、文件上传点、备份功能等）。**先确认前提，再构造利用**，这是写文件类操作能省下最多时间的一条习惯。

**怎么拿到路径**：需要知道目标的绝对路径。实验里用数据库自带的变量查数据目录与安装目录；因为本关不回显，就**回到前面有回显的关卡去查**，拿到路径后回来用。

> 这体现了**漏洞利用常常需要跨点组合**：单点不回显不要紧，只要同一系统上还有另一个能回显的点，就能借它查信息。"借 A 点的回显读 B 点需要的条件"在真实渗透里很常见。

### 3.5 布尔盲注梯队：页面只剩"正常 / 异常"

**变化**：既没有数据回显，也没有报错。

**思路**：把"取数据"改写成一系列**只有真假两答案的判断题**，逐一问数据库。

标准作业顺序是**先猜长度、再猜内容**：

1. 用比较运算二分逼近，先确定目标字符串的长度
2. 在长度确定的前提下，逐位比较字符编码，二分出每一位字符
3. 按"库名 → 表名（先猜各表名长度，再逐字猜内容）→ 列名 → 数据"逐层推进

> **为什么必须"先长度后内容"**：不知道长度就无法确定逐位读取的循环边界；先把长度定下来，后面每一位的猜测才有明确终点。
> **二分法不是"更快的技巧"，而是能否跑完的前提**：逐字符线性猜测的请求量会随数据规模迅速膨胀，二分法把每一位的次数压到对数级。这也是自动化工具内部必须做的优化——理解这一点，才算理解盲注为什么会"慢"。

### 3.6 时间盲注梯队：连真假都没有了

**变化**：页面在两种条件下完全一致。

**思路**：把判断结果编码到**响应耗时**里——让条件成立时立即返回、不成立时等待若干秒，靠"有没有卡住"来区分真假。除延时函数外，还可以用制造计算量的函数作为备选（当延时函数被禁用或被拦截时）。

之后按 3.5 的同一套顺序逐位推进即可。Less 10 与 Less 9 的差别只有闭合符。

## 四、危害

- **数据库层面**：可读取任意库表字段，包括用户凭据与业务数据
- **系统层面**：配合写文件能力可落盘脚本，取得服务器命令执行
- **文件读取层面**：在权限与配置允许时，可读取服务器上的文件
- 本例中完整读出了用户表数据，并成功写入文件取得控制权——**证明了从"一个可控参数"到"服务器失陷"的完整链路**

**利用前提清单（写文件路径）**

- [x] 能写进去 —— 数据库账号具备文件写入权限
- [x] 能访问到 —— 路径可写到 Web 根目录（本例靠路径穿越）
- [x] 能被解析 —— 写入内容为服务端脚本，且该目录允许执行

## 五、修复

| 层级 | 措施 |
|---|---|
| **代码（根治）** | 全部数据访问改用**参数化查询 / 预编译**——让数据永远不进入字符串拼接这一步。这一条解决的是根因，其余都是缓解 |
| 代码 | 输入做类型与格式校验（例如 id 只允许整数，就强制转换后再用） |
| **配置** | **关闭详细报错回显，统一错误页面**——一刀砍掉整个报错梯队 |
| 配置 | 数据库账号遵循最小权限：业务账号不给文件读写权限 |
| 配置 | 文件导入导出相关的配置变量保持默认（即禁止） |
| 配置 | Web 服务与数据库均以低权限用户运行，数据目录不在站点根下 |
| 监测 | 关注含 SQL 关键字、异常编码、超长或畸形参数的请求；关注 Web 目录异常新增文件 |

**哪一条更根本**：参数化查询是根治，因为它**消解了字符串层与语义层的差异**——不是去过滤危险字符，而是让数据在语义上也永远是数据。报错关闭、权限收敛属于纵深防御：它们不修漏洞，但能让利用无处落脚。

## 六、延伸

**三条能带走、且与 payload 无关的判断**：

1. **注入的判定不依赖回显。** 有回显用联合查询，没回显用报错，连报错都没有就用布尔或时间——**"没有回显"不等于"没有漏洞"，只是换了通道**。反过来，评估一个系统时，只要看到"参数拼进 SQL"，就应该假定五条通道都存在。
2. **限制是常态，分段是常态。** 聚合有长度上限、盲注要考虑请求量、时间盲注要考虑超时——真实注入几乎总要在限制里工作。把"一次拿全"当默认预期，是最容易卡住的地方。
3. **写文件类操作先确认前提，再构造利用。** 权限、允许目录、目标目录可写，三条缺一，手法再正确也写不进去。本篇 Less 7 的第一次失败就是这个原因——**先查前提比反复调整输入有效得多**。
