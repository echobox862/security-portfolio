> 自检两条：① 六段是否齐全（现象 / 原理 / 复现 / 危害 / 修复 / 延伸）；② 「原理」一节是否写明了归属哪条框架、为什么成立。

## 一、现象

【一两句说清"看到了什么"，不带解释。例：在头像上传处提交一个脚本后缀的文件，服务端返回成功；直接访问该文件，返回的是脚本执行结果而不是文件内容。】

## 二、原理

【这一节最值钱，也最容易写空。按顺序回答三件事：】

1. **归到哪条框架？** 【例：属 getshell 三元组——写入来自上传功能，访问来自上传目录在站点根下，解析来自该目录对脚本后缀放行。三条都成立，所以链条完整。】
2. **成因是什么？** 【例：服务端用黑名单校验后缀，而黑名单只列举了少数后缀，未覆盖同样会被解析的其他后缀。】
3. **为什么手法能生效、防御为什么没拦住？** 【例：校验只做一次字符串替换，构造后恰好还原出被拦的关键词——这正是"字符串层与语义层不一致"的形态；而黑名单的固有问题就是列举不全。】

> 检验标准：把这一节发给一个没做过这道题的同学，他能不能看懂"为什么能打通"。

## 三、复现

【写成"动作 → 观察 → 判断"的序列，不写可直接复制使用的完整载荷。例：】

1. 【进入某功能点，先正常操作一次，观察请求里有哪些字段会被服务端使用】
2. 【只改动其中一个字段的**类型或位置**（不改内容），观察响应是否变化——由此判断校验发生在哪一层】
3. 【按第 2 步得到的判断构造输入，再次观察响应：返回的是内容本身，还是被执行后的结果】
4. 【打开监控或直接在服务器侧确认落点：文件写到了哪里、以什么后缀存在】

**关键判断点（脱敏）**

```
请求/入口：<接口或功能点>
要改的字段：<哪个字段、为什么是它——写清"怎么找到的">
观察到的现象：<响应内容 / 状态码 / 文件落点>
由此得出的结论：<三元组里满足了哪几条>
```

> **只记录机制，不记录成品**：写入类实验用最小验证内容（能证明"内容被当代码执行"即可），不放任何可用后门。

## 四、危害

【从"能不能被利用"推到"会造成什么后果"，并与风险等级挂钩。例：结合上传目录可被访问与脚本后缀可被解析两个条件，攻击者获得服务器命令执行能力，进而可读取配置文件与业务数据、并以该主机为跳板探测内网。】

【若属写入类，列出利用前提清单，写清楚更显专业：】

- [ ] 能写入（哪个功能或哪条通道）
- [ ] 能访问（路径是否可知、是否在站点根下）
- [ ] 能被解析（哪个后缀、哪个目录允许执行）

## 五、修复

【按「代码 → 配置」两层写。】

| 层级 | 措施 |
|---|---|
| 代码（根治） | 【例：改用白名单校验；对上传文件重命名为随机串；不把用户输入当变量名解析】 |
| 配置 | 【例：上传目录禁止脚本执行；服务以低权限用户运行；关闭详细报错回显】 |
| 监测 | 【例：关注上传目录异常新增文件、含编码特征参数的请求】 |

> 说明一句"哪一条更根本、为什么"——**配置层往往比代码层更有效，因为它改变的是能力边界，而不是试图过滤输入。**

## 六、延伸

【关联到框架与相邻知识点，写能迁移走的判断。例：同一套"过滤只做一次"的缺陷，在 XSS 里表现为关键词双写，在 SQL 注入里表现为关键字双写——共同原理是过滤发生在字符串层、而解析发生在语义层。】
