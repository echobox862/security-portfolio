## 每个工具的 README 必须包含（少一项都不合格）

```markdown
# 工具名

一句话说明它解决什么问题。

## 环境要求
- Python 3.x
- 需要系统安装 xxx（并说明为什么需要，例如 python-nmap 实际调用系统的 nmap 命令）

## 安装
    pip install -r requirements.txt

## 用法
    python xxx.py -H <host> -P <port>
参数说明表格（每个参数：含义、是否必填、默认值）

## 实现思路
- 核心流程分几步
- 用了哪个关键技巧、为什么这样写
  （例：用 connect_ex() 而不是 connect()，因为它返回错误码而不抛异常，
    批量扫描时不需要 try/except 包裹每一次尝试）

## 已知限制
- 例：短超时可能把慢响应的端口误判为关闭
- 例：仅实现 TCP 全连接扫描，未实现 SYN 扫描

## 免责声明
仅用于授权测试与自有环境。
```

## 三条质量要求

1. **必须参数化**。主机、端口、字典路径要能从命令行传入，不写死在代码里——这是"脚本"和"工具"的分界线。
2. **必须有边界控制**。并发数、总尝试次数、超时要可设置且有默认上限。没有上限的爆破/扫描脚本会被认为是危险代码。
3. **必须在 README 里写"已知限制"**。敢说自己的工具哪里不行，比吹得天花乱坠更让人信任——面试官也最吃这一套。

## 不要放进来的东西

- webshell 管理类工具（无论开源与否）——仓库会被误判、也容易违反平台规则
- 含真实目标信息的结果文件（扫描结果、抓包文件）
- 任何"拿到权限之后"的持久化、提权、横向工具
